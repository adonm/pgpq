# postfgb design

Settled decisions for the architecture. The README describes what exists today; this file records where the project is going and why.

## Goal

The smallest Go package that serves OGC API Features over spatial records held in PostgreSQL, at maximum read speed for rustgis.app. Writes are batch-oriented and HTTP-only; the server may rewrite chunks freely. External software (GDAL, rustgis-cli) appears only as a client or a sidecar — the server never links cgo.

## Architecture

Features are encoded into FlatGeobuf chunks (packed Hilbert R-tree included) and stored as bytea. Chunk bounds are scalar floats with a GiST index on their bounding box; the database compares the boxes built from those floats and never parses geometry. Filtering lives in an index sidecar: jsonb/GIN for attributes. huma serves the metadata endpoints; the range-readable file streams from its handler, and an items page is built before its first byte is sent, so a failed read can still answer 500. FlatGeobuf chunks are also served as one range-readable file per collection, so clients read windows in place.

## Storage — one database, one virtual GeoPackage

- `chunks` and `chunk_props` are LIST-partitioned by collection: every collection owns two physical partitions with their own heaps and indexes, which removes today's cross-collection GIN noise and scopes vacuum and drop. A partition is named `chunks_<h>` or `chunk_props_<h>`, where `<h>` is the first 32 hex digits of the SHA-256 of the collection name. Every generated identifier (partitions, staging tables, sort and other indexes) is at most 55 bytes, distinct collections get distinct names, and the hex names cannot match PostgreSQL's own names, so no collection name can collide with another or with a catalog name.
- Chunk ids stay globally unique (identity on the parent). Primary keys: `(collection, id)` and `(collection, chunk_id, feature_ord)`. Sidecar integrity comes from the partition lifecycle, not foreign keys — partitioned FKs would block partition swaps.
- Chunk payloads are zstd-compressed in Go before insert and stored out-of-line uncompressed (`STORAGE EXTERNAL`): Postgres does no compression work and ships stored bytes as-is; checksums and ETags cover the raw FlatGeobuf.
- All queries already carry `collection = $1`, so partition pruning turns access into per-collection index scans with unchanged SQL.
- The `collections` catalog row carries per-collection stats (feature count, spatial and temporal extent, kind, members), operator metadata (title, description, license, keywords) and a `version` that bumps on every replace; the collection endpoints never scan chunk tables. The row also carries a `uid` identity assigned at creation and never reused, so a collection or view deleted and created again under the same name is a new collection to every worker's caches and ETags.
- The core path requires zero PostgreSQL extensions, and nothing probes for optional ones at startup.

## JSON columns and flattening

- A string column whose values hold JSON text is promoted to a Json column at ingest, and its object values are **flattened one level** into ordinary columns named `<parent>_<key>` (keys lower-cased, anything outside `[a-z0-9_]` becomes `_`). Scalar keys are typed (string/long/double/bool, promoted to double or string on mixed evidence); a key whose values are arrays of scalars becomes a Json column carrying the array, so nothing is lost. Nested objects and arrays of objects are left in the parent, which is kept as uploaded.
- The decision is made once, from the first window, and is deterministic: a key must appear in at least two features, at most 24 keys per parent and 64 columns in total, picked by support (ties by name). The chosen keys are filled from every window's features, so a feature carries its flattened values wherever it sits in the upload. Keys that appear only later in the stream stay in the parent column, which is still queryable by containment.
- Performance contract: flattened keys are rows in the same column metadata, so `/queryables` advertises them, the FlatGeobuf schema carries them, and the property-filter path (`?key=value`, CQL2) addresses them like any column. One expression per column serves everything: `cql.ColumnExpr` builds the guarded, literal-key form (`case when jsonb_typeof(props -> 'key') = 'number' then (props ->> 'key')::numeric end`, text/boolean/timestamptz variants), the declared index is created on it, and the CQL builder emits exactly that text when the property is a known column with a matching value. So declaring a flattened key `sortable` gives btree-backed range predicates — PostgreSQL reports an `Index Cond` on the guarded expression for both `=` and `>=`. The builder receives the collection's column casts per request (from the first chunk's column metadata, cached per worker by the collection's uid and version so a replace is seen by every worker), and coerces the bound value first, so a numeric string bound to a numeric column becomes a number and a filter that used to compare text now compares numbers. Unknown properties, values that cannot be coerced, and timestamp columns (whose cast stays text) keep the parameterised CASE form: correct, just unindexed. Equality (`=`, `IN`, `?key=`) is coerced by the same cast before it is matched, so `id = '393226'` and `id = 393226` are one predicate, and so are `c_bool = 'true'` and `c_bool = true`. It is then a containment on the row for every candidate value — `props @> jsonb_build_object(key, value)` for a scalar and `props @> jsonb_build_object(key, jsonb_build_array(value))` for an array *containing* it — so both branches are covered by the sidecar's GIN `jsonb_path_ops` index: an equality filter is a bitmap index scan, not a sequential scan of the sidecar (measured 2.7 s → 12 ms on 4M features). Range predicates still need the expression index, which is what declaring the column `sortable` creates and analyses at ingest: an index scan on a declared column, a sidecar scan on an undeclared one.

## Views — virtual collections

- A view has no data of its own: it is a `collections` row with `kind = 'view'` and an ordered `members` list, created or replaced by PUTting a STAC collection document that carries `members` (or `postfgb:members`) — the document is stored and echoed by the STAC facade like any other, and the view's extent, counts and title come from the members. Members must be native collections that currently have a stored index and byte-identical column metadata, so the composed file describes every member's features correctly; up to 64 members, no filters or column mappings (adding columns from another collection is the separate join work, not a view).
- The composed file is assembled from what the members already store: the header is the first member's header rebuilt with the total feature count, the union envelope and the geometry type that all members share (Unknown when their types differ), the packed R-tree is built by rebasing each member's stored leaves by that member's feature offset, and the run table points at the members' own chunks. No feature byte is copied and no chunk is re-encoded: the view costs one header plus one index — ~40 B/feature, the same as a collection's index — on top of the members.
- Maintenance is part of ingest: a member's commit rebuilds every view that lists it inside the same transaction (the member's fresh segments are readable there), bumps the view's version and prunes the older rows. Reads resolve the layout by version, so a replace flips a view atomically with no stale window. A replace whose column metadata differs from the view's other members is rejected with 422 before anything is committed: the transaction rolls back, so the member and the view keep their previous versions. Tiers are the collection concern: a view always serves full detail, and `overview=` is ignored on a view on every route, `items.fgb` included.
- Views serve the whole read surface. `/items` walks the members in order with the paging offset consumed across them, applying bbox, property and CQL2 predicates per member (identical schemas make that valid) and each member's own time column for `datetime`; `numberMatched` sums the members' counts (omitted with a bbox, as for collections), `queryables` reports the shared column metadata, `/items/{id}` tries each member, and the generated `f=flatgeobuf` export walks the members with the same offset, predicates and `datetime` and writes the matched features under a header whose geometry type is the one they share (Unknown when they differ). Sorting is rejected, and a view always serves tier 0. Dropping a collection rebuilds, in the same transaction, the views that listed it with the members that remain (the stored member list is pruned to them, so queryables and later rebuilds see the same set), and a view whose members all disappear is dropped together with its layout rows.

## Write path — HTTP only

- `PUT /collections/{id}` (writable mode) is content-negotiated. A FlatGeobuf body — the default for any non-JSON content type — creates or replaces the collection from a whole file, not pre-chunked uploads. A JSON body writes catalog metadata: the STAC collection document is stored and echoed by the STAC facade, which serves only the collection documents, and its `title`, `description`, `license` and `keywords` feed the OGC collection. `DELETE /collections/{id}` drops the collection.
- Collection names are 1 to 48 characters: a letter or digit, then letters, digits, `_`, `-` or `.`. `PUT` and `DELETE` answer 422 for any other name. Names are quoted in SQL and hashed into partition names, so case and punctuation need no escaping.
- Loads are transactional: rows go into uncommitted staging tables in the `staging` schema, indexes and overview tiers are built there, and the commit swaps partitions — drop the old ones, move the staged ones into `public` (their indexes keep their final names) and attach them — so parent-level locks last milliseconds. Readers keep serving the previous version for the whole load and see either the old collection or the new one.
- Failure or disconnect rolls back; staging tables disappear with the transaction and loads are retried from scratch (accepted cost).
- Input CRS: any CRS supported by the pure-Go projection layer ([wroge/wgs84](https://github.com/wroge/wgs84)) is reprojected to WGS84 during ingest; anything else is rejected at upload time. Stored geometries are 2D (Z dropped), and chunks declare EPSG:4326.
- The FGB header supplies the uniform schema, and ingest sorts features in bounded windows on the Hilbert curve, so chunking yields spatially coherent chunks and small queries touch few chunks regardless of upload order. Server-side chunking targets roughly 2 MiB per chunk with a self-calibrating byte estimator; overview tiers accumulate to the same target.
- Time column: first DateTime-typed column (overridable with `time_column`). Feature id preference: an id-like property (`id`, `fid`, `gid`, `ogc_fid`, overridable with `id_column`), then the synthetic `chunkID-ord`.
- Sortable columns are declared on the PUT request and indexed during the load (btree expression indexes per partition), which serves range filters on them.
- Loading is a client pipeline, not a server job: ogr2ogr reads any source (GeoParquet via Layercake, databases, files), materializes FlatGeobuf locally and streams it into the same PUT. The server keeps no loader, no background jobs and no format conversion.
- Attributes: every scalar type crosses intact, each at its own width: integers keep every digit across their full range, Float keeps float32 precision, Binary is stored as bytes and shown as base64, and Bool takes true or false. A JSON null is no value, so the item omits the key. A value that does not fit its column (a fraction in an integer column, a number out of range, a number in a Bool column) is stored as no value, never truncated. FlatGeobuf has no list or nested type, and GDAL's FlatGeobuf writer drops the JSON subtype, so list-valued and JSON-subtype columns arrive as JSON text in String columns. Ingest samples the first window per string column and promotes the ones whose values are JSON objects or arrays (majority rule, at least 8 samples) to a FGB `Json` column, unquoting the values: chunks carry real JSON, the props sidecar stores `jsonb` arrays/objects, and the API emits arrays instead of strings. A string that merely starts with `[`/`{` but is not valid JSON stays a string.

## Read path

- The RustGIS project at `/viewer.rgis` carries, per collection, one range-readable `.fgb` layer per overview tier plus full detail, ordered coarsest first and named `<title> · 1%` / `· 10%` / `<title>`, each constrained to its zoom band with the app's `min_scale`/`max_scale` (a layer draws when `max_scale <= 1:scale <= min_scale`; tiers are probed per collection and `overview=` falls back to full detail when a tier is missing). All layers are `visible: false`; RustGIS has no layer-group node (its folders are filesystem paths) and no live OGC API Features layer kind — its service flow pages the collection and materializes it — so a zoom-switching set of file layers plus a `service_groups` record pointing at the collection list is how a project expresses both.
- The read surface is CORS-open (`Access-Control-Allow-Origin: *`, ETag and Content-Crs exposed) so browser clients — the RustGIS web app that `/viewer` redirects to (`web.rustgis.app/?embed&project=…`, fed by the project generated at `/viewer.rgis`: range-readable FlatGeobuf layers, all hidden by default), or any RustGIS build elsewhere — can query any deployment directly; the browser tooling is RustGIS itself, not a second API.

- Unfiltered scans stream chunk windows in id order with no fixed chunk cap; offset paging stays exact at any collection size: `offset=k` returns features k..k+n-1 of the list that `limit=100000` returns, and with a `bbox` the offset counts only features that pass the exact bbox test.
- Filtered fan-out runs under a per-request byte budget (`--max-chunk-bytes`, 32 MiB by default) so windows stay bounded no matter how large individual chunks are. A page is filled before it is returned: with a bbox the matches are tested exactly after the index prune, so the walk continues through further match windows until the page is full or the matches run out. A page is short only when it is the last one.
- Read errors answer 500, never a short page. A chunk that cannot be fetched or decoded answers 500 for any request that reaches it, with the error logged and the chunk named; a page that ends before that chunk is unaffected. A walk that reaches the end of a tier-0 collection without filling its page (no filter, no bbox) checks the chunks it listed against the collection's `chunk_count` and `feature_count`, so a missing or inconsistent chunk row answers 500 and a short page cannot quietly disagree with `numberMatched`; a full page is answered as it is, and the next short one reports the inconsistency. A feature the JSON encoder cannot represent fails the page the same way. A virtual FlatGeobuf range that fails after its headers are sent ends short of its declared length and is logged, because the status is already out.
- `numberMatched` is omitted whenever a bbox is set. A bbox is tested per feature after the chunk prune, so an exact count walks every candidate feature (about 5 s for the 294,408 matches of `building='yes'` in `bbox=-1,52,0,53` on buildings_fr); the index-only count it would replace over-counted (310,858).
- Filtered paging keeps `(chunk_id, feature_ord)` order and always runs the index-driven query: the sort key is `chunk_id + 0`, so the planner never walks the primary key to find rare matches, and the GIN sidecar (or a declared sort index) drives a bitmap scan plus sort. New partitions are `analyze`d inside the commit, so plans are right from the first query after a load instead of after autovacuum catches up.
- Items: GeoJSON default; `f=flatgeobuf` (or the `.fgb` address) streams full detail as a single FGB, declaring the geometry type that the written features share (Unknown when they differ); for views, members are walked in order and re-encoded under the first member's columns, honouring `limit`, `offset` and `datetime` as `/items` does. Default page 100,000 (also for FlatGeobuf), max 1,000,000. `/items.fgb` without filter parameters is not a generated stream but a virtual file: magic + a collection header + a packed R-tree rebuilt from the chunk indexes (leaf offsets rebased into the concatenated feature streams) + the chunks' bare feature bytes, served with `Accept-Ranges` and RFC 7233 range responses (206, `Content-Range`, ETag from the collection's `uid`, tier and version, `If-None-Match` → 304). The header and index are built **at ingest** — the header is the first chunk's header with the total feature count and the envelope, and it declares the geometry type that all the collection's chunks share (Unknown when they differ); every chunk's index leaves are rebased into the growing feature stream as the chunk is written, and the packed tree is assembled and stored in ~1 MiB `virtual_segment` rows alongside a `virtual_file` layout row, all keyed by `(collection, tier, version)`; `chunks.feature_bytes` records each chunk's feature-region length, so the run table is a window sum over the partition. Nothing is built per worker and nothing is held in memory: a read resolves the layout once per version, streams header and index bytes from the segments a range overlaps, and slices the chunks those bytes fall in, decompressing only the chunks it touches (decompressed chunks stay in a worker-wide 64 MiB cache keyed by collection, chunk and version, so repeated window reads do not pay it again). Items pages walk the same way, decoding each chunk's features across the cores: 100k records of a 4M-feature collection take ~1.2 s as 35 MB of GeoJSON, 4.8 MB with zstd, and deep offsets skip whole chunks by their feature counts. An items page is held in memory until its walk completes (35 MB for the default 100k records of a 4M-feature collection, so concurrent large pages cost their size in RAM), which is what lets a failed walk answer 500 instead of a short 200. An ingest that fails to store a layout leaves the collection unreadable through `/items.fgb` — the ingest path must always build it (there is no lazy fallback). A range that does not fall in any chunk (or any byte past the last run) is padded. A view has no chunks of its own: its file reuses the members' — one header, one packed R-tree built from their stored leaves and a run table pointing at their chunks — so nothing is re-encoded and the only added storage is the view's own header and index. `overview=auto|0|1|2` overrides tier selection for unfiltered requests; filters, views and generated exports always read full detail. `numberMatched` is opt-in. `/collections/{id}/items/{featureId}` serves one feature.
- Tiers are ordinary collections data: an overview tier is just another set of chunks, so `overview=` serves it as the same virtual FlatGeobuf and clients switch layers by zoom themselves. The OGC Features surface serves full detail unless `overview=1|2` asks otherwise — a default tier would silently sample the data and stop paging at the tier's size. `/items/{id}` takes no `overview` and resolves only full-detail features, so a tier's synthetic `chunkID-ord` id is not a feature.
- Overview tiers: ordinal stride 10 / 100 with Douglas-Peucker simplification (only for geometries larger than the tolerance — small polygons are kept whole), so building layers get real tiers too; ~10-15% extra storage; a collection without tiers falls back to full detail.
- Queryables come from catalog columns; `datetime` filters the recorded time column (per member on views); `sortby` and `q` are not supported and answer 400; `crs` and `bbox-crs` accept only CRS84 and answer 400 for any other value, and a GeoJSON response to a `crs` request carries `Content-Crs` set to CRS84; CQL2 text covers comparisons, `IN`/`BETWEEN`/`LIKE`/`IS NULL` and `AND`/`OR`/`NOT`, and `filter-lang` other than `cql2-text` answers 400; `bbox` is the spatial filter, and spatial functions such as `S_INTERSECTS` are not supported and answer 400. Equality on a JSON array matches its members (`props @> jsonb_build_object(k, v)` or `props -> k @> jsonb_build_array(v)`), so list-valued tags filter like scalars. An equality value is coerced by the column's cast first: a numeric string on a numeric column becomes a number, and `'true'` or `'false'` on a boolean column become booleans. A typed value then also matches its string form, because a String column holds `'2'` while `?building:levels=2` arrives as the number 2. A value that does not coerce (`'abc'` on a number column, `'yes'` on a boolean column, `'Inf'` or `'NaN'`) matches its text only and never errors. CQL2-text identifiers stop at colons, so colon-named OSM keys (`addr:street`) go through `{property}=` query parameters. Ordered comparisons and `LIKE` read the array's text form.
- Conformance classes are only claimed when implemented — no over-claiming.
- The STAC facade is a read-only echo of the stored collection documents (`/stac/collections`, `/stac/collections/{id}`); it serves no STAC catalog, items or search, so it claims no STAC conformance class. Its links point only at routes it serves: `self`, and `parent` from a collection to the list.

## HTTP caching

Responses negotiate content encoding: `Accept-Encoding` picks zstd (klauspost/compress, already used for chunks) over gzip for JSON and GeoJSON, with `Vary: Accept-Encoding`. Virtual FlatGeobufs carry ETags built from the collection's `uid`, the overview tier and the `version`, and workers cache virtual files under the same key. A replace bumps the version (a view's version bumps whenever a member is rebuilt), and a delete followed by a create gets a new `uid`, so no ETag or cache key repeats in any worker process. Items stay uncached.

## Exports

There is no server-side format conversion: `items?f=flatgeobuf` is the bulk download, and clients convert locally with GDAL or any OGR binding. The server stays a single dependency-free binary.

## Ops and build

- Images build with [ko](https://ko.build): no Dockerfile, static base (`cgr.dev/chainguard/static`), CGO_ENABLED=0, git-SHA tags, SBOM support.
- mise provides Go, just, hk and ko. hk runs gofmt/vet/tidy/tests on every commit; GitHub Actions runs unit tests, PostgreSQL-backed integration tests (ingest → query → staged replace → delete) against a service container, and a ko image build. `just test-integration` runs the same tests locally against the compose database.
- `/healthz` liveness and `/readyz` readiness (database ping plus migration check); a minimal hand-rolled Prometheus `/metrics` covering requests, durations, response bytes, ingest outcomes and pool gauges; SIGTERM/SIGINT graceful shutdown; `--max-conns`/`--min-conns` pool flags; structured request logs (method, path, route, status, duration, bytes). Deployment stays raw binary / generated image; no release pipeline yet.
- Workers run in two modes: writable (ingest and delete) and readonly (only the OGC and STAC read surface; writes are not registered, migrations are skipped by default). The server does no authentication — production deploys terminate auth in an adjacent layer (Kubernetes Gateway API, reverse proxy or service mesh) and expose only readonly workers publicly. `--addr` defaults to `127.0.0.1:8080` so a bare `postfgb serve` never binds a public interface; deployments pass an explicit `--addr` (e.g. `:8080`) on the network they intend to serve. Filtered endpoints always filter server-side.

## Performance

Design target: ~100M features in one collection on one PostgreSQL node. Chunk fetches run in parallel within a request; every request carries a chunk byte budget; virtual FlatGeobuf headers and indexes are built once per version in each worker, so range reads cost one chunk fetch per touched chunk. Measured baseline (1M synthetic features, GDAL as OGC client): full paged scan ~69s, single FlatGeobuf export 7s, bbox page ~2s.

## Rejected or deferred

- Virtual PMTiles archives and the go-pmtiles dependency (removed), and vector tiles as an interface: a range-readable FlatGeobuf per collection replaces the MVT endpoint, the tile cache and the tile matrix set surface (tile code dropped once in-place FlatGeobuf reads worked in GDAL and RustGIS).
- Materialized views and DB-native view discovery; views of views.
- Dynamic per-collection tables and schema-per-collection storage.
- Async ingest jobs and upload sessions (push stays a synchronous, transactional replace); versioned blue/green replace. STAC pull ingests and an adjacent ogr2ogr loader: loading is a client-side pipeline that streams FlatGeobuf into the same PUT, so the server keeps no background jobs and stays a single dependency-free binary.
- cgo PROJ; the rustgis-cli export engine; server-side format conversion (clients convert FlatGeobuf locally); runtime extension accelerators (nothing probes for them; the core path needs none).
- Server-side auth (bearer tokens, API keys, OAuth): the app ships no auth; production terminates auth in an adjacent layer and picks the worker mode (writable/readonly) that matches the route it is deployed on.
- Removed: the raw chunk and manifest endpoints (`/items.fgb` serves chunk-level reads in place), the `/stats` catalog totals (not an OGC or STAC surface), fulltext (`q`: no conformance class claims it, and its `chunk_text` tsvector sidecar duplicated every text attribute at ingest), `sortby` (no conformance class claims it; declared sortable columns still serve range filters), and CRS negotiation beyond CRS84 (ingest still reprojects uploads). `sortby` and `q`, and any `crs` or `bbox-crs` other than CRS84, answer 400.
- Removed: the per-collection `layers.<name>` SQL views (nothing read them; migration 0021 drops them with their schema), the startup `pg_available_extensions` probe, and the `collections.sortable` catalog column (the declared sort indexes serve range filters; migration 0022 drops the column).
- Removed: S2 coverings (bounding-box pruning is enough because features are tested exactly after pruning).
- Removed: spatial CQL2 functions (`S_INTERSECTS`, with the polyclip-go intersection engine and the WKT parser). `bbox` covers the spatial filter; features are not tested against polygons, and spatial functions answer 400.
- Removed: CQL2-JSON (`filter-lang=cql2-json`, and a JSON `filter` in the STAC search body). The clients in use (GDAL, RustGIS) send CQL2 text, which is now the only filter encoding; any other `filter-lang` answers 400.
- Removed: the HTML host page at `/viewer` (an iframe, toolbar and CSS around the RustGIS app). `/viewer` is now a 302 to `web.rustgis.app/?embed&project=…`, which reads `/viewer.rgis` itself, so the page added nothing the redirect does not.
- Removed: the STAC catalog, STAC items and STAC search (`/stac`, `/stac/collections/{id}/items`, `/stac/search`). Items and search duplicated the OGC items endpoint, which the clients in use read at `/collections/{id}/items`, and the STAC core and item-search conformance claims went with them.

## Build order

1. ko image builds (mise, .ko.yaml, just recipes, CI job).
2. Partitioned storage, catalog stats, layers views, `pg_trgm` removal.
3. HTTP FlatGeobuf ingest: PUT/delete, transactional replace, reprojection, declared sortables; remove the ingest CLI.
4. Read correctness: windowed streaming, `overview=`, single-feature endpoint and ids, `numberMatched`, queryables.
5. Union views serving.
6. Client features: datetime, sortby, CRS/bbox-crs, CQL2 spatial.
7. Exports through ogr2ogr only.
8. Ops: healthz/readyz, metrics, lifecycle and pool flags, integration tests in CI.
9. Performance: parallel chunk fetch, byte budget, version-keyed manifest ETags, in-place FlatGeobuf reads (virtual files) instead of rendered tiles.
10. STAC: read-only API facade (catalog, collections, items, search) over the same collections; collection metadata arrives as the JSON body of `PUT /collections/{id}`.
