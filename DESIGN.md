# postfgb design

Settled decisions for the architecture. The README describes what exists today; this file records where the project is going and why.

## Goal

The smallest Go package that serves OGC API Features over spatial records held in PostgreSQL, at maximum read speed for rustgis.app. Writes are batch-oriented and HTTP-only; the server may rewrite chunks freely. External software (GDAL, rustgis-cli) appears only as a client or a sidecar — the server never links cgo.

## Architecture

Features are encoded into FlatGeobuf chunks (packed Hilbert R-tree included) and stored as bytea. Chunk bounds are scalar floats with a GiST index on their bounding box; the database compares the boxes built from those floats and never parses geometry. Filtering lives in an index sidecar: jsonb/GIN for attributes. huma serves the metadata endpoints; items and the range-readable file stream from handlers. FlatGeobuf chunks are also served as one range-readable file per collection, so clients read windows in place.

## Storage — one database, one virtual GeoPackage

- `chunks` and `chunk_props` are LIST-partitioned by collection: every collection owns two physical partitions with their own heaps and indexes, which removes today's cross-collection GIN noise and scopes vacuum and drop.
- Chunk ids stay globally unique (identity on the parent). Primary keys: `(collection, id)` and `(collection, chunk_id, feature_ord)`. Sidecar integrity comes from the partition lifecycle, not foreign keys — partitioned FKs would block partition swaps.
- Chunk payloads are zstd-compressed in Go before insert and stored out-of-line uncompressed (`STORAGE EXTERNAL`): Postgres does no compression work and ships stored bytes as-is; checksums and ETags cover the raw FlatGeobuf.
- All queries already carry `collection = $1`, so partition pruning turns access into per-collection index scans with unchanged SQL.
- Each collection also gets a `layers.<name>` SQL view over its tier-0 chunks for database-side introspection, GeoPackage-style.
- The `collections` catalog row carries per-collection stats (feature count, spatial and temporal extent, kind, members, declared sortable columns), operator metadata (title, description, license, keywords) and a `version` that bumps on every replace; the collection endpoints never scan chunk tables.
- The core path requires zero PostgreSQL extensions; the legacy `pg_trgm` create is removed.

## JSON columns and flattening

- A string column whose values hold JSON text is promoted to a Json column at ingest, and its object values are **flattened one level** into ordinary columns named `<parent>_<key>` (keys lower-cased, anything outside `[a-z0-9_]` becomes `_`). Scalar keys are typed (string/long/double/bool, promoted to double or string on mixed evidence); a key whose values are arrays of scalars becomes a Json column carrying the array, so nothing is lost. Nested objects and arrays of objects are left in the parent, which is kept as uploaded.
- The decision is made once, from the first window, and is deterministic: a key must appear in at least two features, at most 24 keys per parent and 64 columns in total, picked by support (ties by name). Keys that appear only later in the stream stay in the parent column, which is still queryable by containment.
- Performance contract: flattened keys are rows in the same column metadata, so `/queryables` advertises them, the FlatGeobuf schema carries them, and the property-filter path (`?key=value`, CQL2) addresses them like any column. One expression per column serves everything: `cql.ColumnExpr` builds the guarded, literal-key form (`case when jsonb_typeof(props -> 'key') = 'number' then (props ->> 'key')::numeric end`, text/boolean/timestamptz variants), the declared index is created on it, and the CQL builder emits exactly that text when the property is a known column with a matching value. So declaring a flattened key `sortable` gives btree-backed range predicates — PostgreSQL reports an `Index Cond` on the guarded expression for both `=` and `>=`. The builder receives the collection's column casts per request (from the first chunk's column metadata), and coerces the bound value first, so a numeric string bound to a numeric column becomes a number and a filter that used to compare text now compares numbers. Unknown properties, values that cannot be coerced, and timestamp columns (whose cast stays text) keep the parameterised CASE form: correct, just unindexed. Equality is a containment on the row for every candidate value — `props @> jsonb_build_object(key, value)` for a scalar and `props @> jsonb_build_object(key, jsonb_build_array(value))` for an array *containing* it — so both branches are covered by the sidecar's GIN `jsonb_path_ops` index: an equality filter is a bitmap index scan, not a sequential scan of the sidecar (measured 2.7 s → 12 ms on 4M features). Range predicates still need the expression index, which is what declaring the column `sortable` creates and analyses at ingest: an index scan on a declared column, a sidecar scan on an undeclared one.

## Views — virtual collections

- A view has no data of its own: it is a `collections` row with `kind = 'view'` and an ordered `members` list, created or replaced by PUTting a STAC collection document that carries `members` (or `postfgb:members`) — the document is stored and echoed by the STAC facade like any other, and the view's extent, counts and title come from the members. Members must be native collections that currently have a stored index and byte-identical column metadata, so the composed file describes every member's features correctly; up to 64 members, no filters or column mappings (adding columns from another collection is the separate join work, not a view).
- The composed file is assembled from what the members already store: the header is the first member's header rebuilt with the total feature count and the union envelope, the packed R-tree is built by rebasing each member's stored leaves by that member's feature offset, and the run table points at the members' own chunks. No feature byte is copied and no chunk is re-encoded: the view costs one header plus one index — ~40 B/feature, the same as a collection's index — on top of the members.
- Maintenance is part of ingest: a member's commit rebuilds every view that lists it inside the same transaction (the member's fresh segments are readable there), bumps the view's version and prunes the older rows. Reads resolve the layout by version, so a replace flips a view atomically with no stale window. Tiers are the collection concern: a view always serves full detail, and `overview=` on a view falls back to tier 0.
- Views serve the whole read surface. `/items` walks the members in order with the paging offset consumed across them, applying bbox, property and CQL2 predicates per member (identical schemas make that valid) and each member's own time column for `datetime`; `numberMatched` sums the members' counts, `queryables` reports the shared column metadata, `/items/{id}` tries each member, and the generated `f=flatgeobuf` export concatenates the members' raw features under the first member's header without re-encoding them. Sorting is rejected, and a view always serves tier 0. Dropping a collection rebuilds the views that listed it, and a view whose members all disappear is dropped.

## Write path — HTTP only

- `PUT /collections/{id}` (writable mode) is content-negotiated. A FlatGeobuf body — the default for any non-JSON content type — creates or replaces the collection from a whole file, not pre-chunked uploads. A JSON body writes catalog metadata: the STAC collection document is stored and echoed by the STAC facade, and its `title`, `description`, `license` and `keywords` feed the OGC collection. `DELETE /collections/{id}` drops the collection.
- Loads are transactional: rows go into uncommitted staging tables, indexes and overview tiers are built there, and the commit swaps partitions — drop the old ones, attach the staged ones — so parent-level locks last milliseconds. Readers keep serving the previous version for the whole load and see either the old collection or the new one.
- Failure or disconnect rolls back; staging tables disappear with the transaction and loads are retried from scratch (accepted cost).
- Input CRS: any CRS supported by the pure-Go projection layer ([wroge/wgs84](https://github.com/wroge/wgs84)) is reprojected to WGS84 during ingest; anything else is rejected at upload time. Stored geometries are 2D (Z dropped), and chunks declare EPSG:4326.
- The FGB header supplies the uniform schema, and ingest sorts features in bounded windows on the Hilbert curve, so chunking yields spatially coherent chunks and small queries touch few chunks regardless of upload order. Server-side chunking targets roughly 2 MiB per chunk with a self-calibrating byte estimator; overview tiers accumulate to the same target.
- Time column: first DateTime-typed column (overridable with `time_column`). Feature id preference: an id-like property (`id`, `fid`, `gid`, `ogc_fid`, overridable with `id_column`), then the synthetic `chunkID-ord`.
- Sortable columns are declared on the PUT request and indexed during the load (btree expression indexes per partition), which serves range filters on them.
- Loading is a client pipeline, not a server job: ogr2ogr reads any source (GeoParquet via Layercake, databases, files), materializes FlatGeobuf locally and streams it into the same PUT. The server keeps no loader, no background jobs and no format conversion.
- Attributes: every scalar type crosses intact. FlatGeobuf has no list or nested type, and GDAL's FlatGeobuf writer drops the JSON subtype, so list-valued and JSON-subtype columns arrive as JSON text in String columns. Ingest samples the first window per string column and promotes the ones whose values are JSON objects or arrays (majority rule, at least 8 samples) to a FGB `Json` column, unquoting the values: chunks carry real JSON, the props sidecar stores `jsonb` arrays/objects, and the API emits arrays instead of strings. A string that merely starts with `[`/`{` but is not valid JSON stays a string.

## Read path

- The RustGIS project at `/viewer.rgis` carries, per collection, one range-readable `.fgb` layer per overview tier plus full detail, ordered coarsest first and named `<title> · 1%` / `· 10%` / `<title>`, each constrained to its zoom band with the app's `min_scale`/`max_scale` (a layer draws when `max_scale <= 1:scale <= min_scale`; tiers are probed per collection and `overview=` falls back to full detail when a tier is missing). All layers are `visible: false`; RustGIS has no layer-group node (its folders are filesystem paths) and no live OGC API Features layer kind — its service flow pages the collection and materializes it — so a zoom-switching set of file layers plus a `service_groups` record pointing at the collection list is how a project expresses both.
- The read surface is CORS-open (`Access-Control-Allow-Origin: *`, ETag and Content-Crs exposed) so browser clients — the RustGIS web app embedded by the minimal `/viewer` host (an iframe on `web.rustgis.app/?embed&project=…`, fed by the project generated at `/viewer.rgis`: range-readable FlatGeobuf layers, all hidden by default), or any RustGIS build elsewhere — can query any deployment directly; the browser tooling is RustGIS itself, not a second API.

- Unfiltered scans stream chunk windows in id order with no fixed chunk cap; offset paging stays exact at any collection size.
- Filtered fan-out runs under a per-request byte budget (`--max-chunk-bytes`, 32 MiB by default) so windows stay bounded no matter how large individual chunks are; short pages always carry honest next links.
- Filtered paging keeps `(chunk_id, feature_ord)` order but never lets the planner walk the primary key to find rare matches: the ordered query runs under a short budget (500 ms plus 20 µs per requested feature, capped at 4 s), and if it is cancelled the same ordering is re-run so the GIN sidecar index drives a bitmap scan plus sort. New partitions are `analyze`d inside the commit, so plans are right from the first query after a load instead of after autovacuum catches up.
- Items: GeoJSON default; `f=flatgeobuf` (or the `.fgb` address) streams full detail as a single FGB — for views, members are walked in order under one union schema (mapped column names, promoted types) and re-encoded, honouring `limit` and `offset`. Default page 100,000 (also for FlatGeobuf), max 1,000,000. `/items.fgb` without filter parameters is not a generated stream but a virtual file: magic + a collection header + a packed R-tree rebuilt from the chunk indexes (leaf offsets rebased into the concatenated feature streams) + the chunks' bare feature bytes, served with `Accept-Ranges` and RFC 7233 range responses (206, `Content-Range`, ETag from the collection version, `If-None-Match` → 304). The header and index are built **at ingest** — every chunk's index leaves are rebased into the growing feature stream as the chunk is written, and the packed tree is assembled and stored in ~1 MiB `virtual_segment` rows alongside a `virtual_file` layout row, all keyed by `(collection, tier, version)`; `chunks.feature_bytes` records each chunk's feature-region length, so the run table is a window sum over the partition. Nothing is built per worker and nothing is held in memory: a read resolves the layout once per version, streams header and index bytes from the segments a range overlaps, and slices the chunks those bytes fall in, decompressing only the chunks it touches (decompressed chunks stay in a worker-wide 64 MiB cache keyed by collection, chunk and version, so repeated window reads do not pay it again). Items pages walk the same way, decoding each chunk's features across the cores: 100k records of a 4M-feature collection take ~1.2 s as 35 MB of GeoJSON, 4.8 MB with zstd, and deep offsets skip whole chunks by their feature counts. An ingest that fails to store a layout leaves the collection unreadable through `/items.fgb` — the ingest path must always build it (there is no lazy fallback). A range that does not fall in any chunk (or any byte past the last run) is padded. A view has no chunks of its own: its file reuses the members' — one header, one packed R-tree built from their stored leaves and a run table pointing at their chunks — so nothing is re-encoded and the only added storage is the view's own header and index. `overview=auto|0|1|2` overrides tier selection for unfiltered requests; filters and generated exports always read full detail. `numberMatched` is opt-in. `/collections/{id}/items/{featureId}` serves one feature.
- Tiers are ordinary collections data: an overview tier is just another set of chunks, so `overview=` serves it as the same virtual FlatGeobuf and clients switch layers by zoom themselves. The OGC Features surface serves full detail unless `overview=1|2` asks otherwise — a default tier would silently sample the data and stop paging at the tier's size.
- Overview tiers: ordinal stride 10 / 100 with Douglas-Peucker simplification (only for geometries larger than the tolerance — small polygons are kept whole), so building layers get real tiers too; ~10-15% extra storage; a collection without tiers falls back to full detail.
- Queryables come from catalog columns; `datetime` filters the recorded time column (per member on views); `sortby` and `q` are not supported and answer 400; `crs` and `bbox-crs` accept only CRS84 and answer 400 for any other value, and a GeoJSON response to a `crs` request carries `Content-Crs` set to CRS84; CQL2 text and JSON cover comparisons, `IN`/`BETWEEN`/`LIKE`/`IS NULL`, and spatial `S_INTERSECTS` with polygonal WKT or GeoJSON (top-level AND only) implemented with polyclip-go over an in-house WKT parser. Equality on a JSON array matches its members (`props @> jsonb_build_object(k, v)` or `props -> k @> jsonb_build_array(v)`), so list-valued tags filter like scalars; numeric and boolean literals also match their string form, because FlatGeobuf stores every attribute as text and `?building:levels=2` arrives as a number — CQL2-text identifiers stop at colons, so colon-named OSM keys (`addr:street`) go through `filter-lang=cql2-json` or `{property}=` query parameters. Ordered comparisons and `LIKE` read the array's text form.
- Conformance classes are only claimed when implemented — no over-claiming.

## HTTP caching

Responses negotiate content encoding: `Accept-Encoding` picks zstd (klauspost/compress, already used for chunks) over gzip for JSON and GeoJSON, with `Vary: Accept-Encoding`. Virtual FlatGeobufs carry ETags derived from a monotonically increasing per-collection `version` (views combine member versions); virtual files are cached per version in the worker, so a replace invalidates them by construction. Items stay uncached.

## Exports

There is no server-side format conversion: `items?f=flatgeobuf` is the bulk download, and clients convert locally with GDAL or any OGR binding. The server stays a single dependency-free binary.

## Ops and build

- Images build with [ko](https://ko.build): no Dockerfile, static base (`cgr.dev/chainguard/static`), CGO_ENABLED=0, git-SHA tags, SBOM support.
- mise provides Go, just, hk and ko. hk runs gofmt/vet/tidy/tests on every commit; GitHub Actions runs unit tests, PostgreSQL-backed integration tests (ingest → query → staged replace → delete) against a service container, and a ko image build. `just test-integration` runs the same tests locally against the compose database.
- `/healthz` liveness and `/readyz` readiness (database ping plus migration check); a minimal hand-rolled Prometheus `/metrics` covering requests, durations, response bytes, ingest outcomes and pool gauges; SIGTERM/SIGINT graceful shutdown; `--max-conns`/`--min-conns` pool flags; structured request logs (method, path, route, status, duration, bytes). Deployment stays raw binary / generated image; no release pipeline yet.
- Workers run in two modes: writable (ingest and delete) and readonly (only the OGC and STAC read surface; writes are not registered, migrations are skipped by default). The server does no authentication — production deploys terminate auth in an adjacent layer (Kubernetes Gateway API, reverse proxy or service mesh) and expose only readonly workers publicly. `--addr` defaults to `127.0.0.1:8080` so a bare `postfgb serve` never binds a public interface; deployments pass an explicit `--addr` (e.g. `:8080`) on the network they intend to serve. Filtered endpoints always filter server-side.

## Performance

Design target: ~100M features in one collection on one PostgreSQL node. Chunk fetches run in parallel within a request; every request carries a chunk byte budget; virtual FlatGeobuf headers and indexes are built once per version in each worker, so range reads cost one chunk fetch per touched chunk. Measured baseline (1M synthetic features, GDAL as OGC client): full paged scan ~69s, single FlatGeobuf export 7s, bbox page ~2s.

## Rejected or deferred

- Virtual PMTiles archives and the go-pmtiles dependency (removed), and vector tiles as an interface: a range-readable FlatGeobuf per collection replaces the MVT endpoint, the tile cache and the tile matrix set surface (tile code dropped once in-place FlatGeobuf reads worked in GDAL and RustGIS).
- Materialized views and DB-native view discovery; views of views.
- Dynamic per-collection tables and schema-per-collection storage.
- Async ingest jobs and upload sessions (push stays a synchronous, transactional replace); versioned blue/green replace. STAC pull ingests and an adjacent ogr2ogr loader: loading is a client-side pipeline that streams FlatGeobuf into the same PUT, so the server keeps no background jobs and stays a single dependency-free binary.
- cgo PROJ; the rustgis-cli export engine; server-side format conversion (clients convert FlatGeobuf locally); runtime extension accelerators (probing stays as a future hook).
- Server-side auth (bearer tokens, API keys, OAuth): the app ships no auth; production terminates auth in an adjacent layer and picks the worker mode (writable/readonly) that matches the route it is deployed on.
- Removed: the raw chunk and manifest endpoints (`/items.fgb` serves chunk-level reads in place), the `/stats` catalog totals (not an OGC or STAC surface), fulltext (`q`: no conformance class claims it, and its `chunk_text` tsvector sidecar duplicated every text attribute at ingest), `sortby` (no conformance class claims it; declared sortable columns still serve range filters), and CRS negotiation beyond CRS84 (ingest still reprojects uploads). `sortby` and `q`, and any `crs` or `bbox-crs` other than CRS84, answer 400.
- Removed: S2 coverings (bounding-box pruning is enough because features are tested exactly after pruning).

## Build order

1. ko image builds (mise, .ko.yaml, just recipes, CI job).
2. Partitioned storage, catalog stats, layers views, `pg_trgm` removal.
3. HTTP FlatGeobuf ingest: PUT/delete, transactional replace, reprojection, declared sortables; remove the ingest CLI.
4. Read correctness: windowed streaming, `overview=`, single-feature endpoint and ids, `numberMatched`, queryables.
5. Union views serving.
6. Client features: datetime, sortby, CRS/bbox-crs, CQL2 spatial.
7. Exports through ogr2ogr only.
8. Ops: healthz/readyz, metrics, lifecycle and pool flags, integration tests in CI.
9. Performance: parallel chunk fetch, byte budget, version-keyed manifest ETags, in-place FlatGeobuf reads (virtual files) instead of rendered tiles.
10. STAC: read-only API facade (catalog, collections, items, search) over the same collections; collection metadata arrives as the JSON body of `PUT /collections/{id}`.
