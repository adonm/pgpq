Design contract · C4 + Diátaxis

One collection. One virtual GeoParquet 2.0 file.

pgpq v2 keeps complete, immutable native GeoParquet 2.0 shards in PostgreSQL and serves them as one logical file. Producers upload finished files; clients read HTTP ranges and do bbox and filter work locally. The server validates, stores, merges and stitches bytes: it never converts or queries.

System context

C4 L1

Who uses pgpq and what sits outside it. No internal components or request ordering.

Assumptions

  • One PostgreSQL stores the catalog, shard bytes, synthesized footers and the id index.
  • The producer is external; pgpq has no converter or query engine.
  • Public reads use readonly workers; only the writable worker accepts uploads.
  • No auth or TLS inside pgpq; the adjacent proxy owns both.

Dynamic view · PUT replace

C4 dynamic

One upload replaces the whole collection. The new version becomes visible in one transaction; the old version stays readable while a client or version references it.

Dynamic view · POST upsert / merge

C4 dynamic

One batch upserts by id. Only shards that hold replaced rows or overlap the new key range are rewritten; everything else is referenced unchanged.

Dynamic view · virtual Range read

C4 dynamic

The served file is logical: leading PAR1, shard payloads and one footer, with offsets that map back to PostgreSQL chunks. There is no separate manifest; clients discover layout from the footer. The server stitches ranges; decoding and filtering happen in the client.

  • HEAD and GET return Content-Length, Accept-Ranges: bytes and the version ETag. A full response is 200; a range response is 206.
  • The client reads the trailing eight bytes for footer length and PAR1, then fetches the synthesized footer.
  • Footer offsets are rebased. virtual_base plus shard data_start and data_end translate each virtual range to stored bytes; the server stitches ranges that cross shards.
  • The client fetches only the column chunks it needs, decodes them, then applies its own bbox and attribute filters. There is no server-side predicate evaluation.

How to produce, upload and read

Diátaxis how-to

DuckDB is the external producer. The server never runs DuckDB or GDAL; it accepts only the native 2.0 file that DuckDB writes.

1 · Produce a native 2.0 file

INSTALL spatial;
LOAD spatial;

COPY (
  SELECT id, geom, name
  FROM read_parquet('/data/buildings.parquet')
) TO '/tmp/buildings-v2.parquet'
  (FORMAT parquet,
   GEOPARQUET_VERSION 'V2',
   COMPRESSION zstd);

Use DuckDB 1.5.6 or newer with the spatial extension. geom must already be a geometry in OGC:CRS84 or EPSG:4326. There is no GDAL container and no server-side conversion.

2 · PUT a replacement

curl -X PUT -T /tmp/buildings-v2.parquet \
  -H 'Content-Type: application/vnd.apache.parquet' \
  'http://localhost:8080/v2/collections/buildings'

Send the same body with POST to upsert by id. A successful write returns JSON with collection, version, features, shards, bytes and etag.

3 · Read it as one file

INSTALL spatial;
LOAD spatial;
INSTALL httpfs;
LOAD httpfs;

SELECT id, name
FROM read_parquet(
  'http://localhost:8080/v2/collections/buildings.parquet')
WHERE ST_Intersects(
  geom,
  ST_MakeEnvelope(7.40, 43.70, 7.45, 43.76));

DuckDB uses HTTP Range to fetch the footer and the column chunks it needs. The bbox is evaluated locally.

4 · Check headers and ranges

URL=http://localhost:8080/v2/collections/buildings.parquet
curl -sI "$URL"
curl -s -H 'Range: bytes=0-3' "$URL" | xxd
curl -s -H 'Range: bytes=-8' "$URL" | xxd
curl -s -o /dev/null -w '%{http_code}\n' \
  -H 'Range: bytes=0-3' "$URL"

The first range should contain PAR1; the last eight bytes contain the footer length and the trailing PAR1. A plain GET still works, but reads the whole virtual file.

Parquet responses use application/vnd.apache.parquet, a version ETag of the form pgpq-{id}-v{version} and Cache-Control: no-cache. Status codes: 200 full body, 206 range, 404 unknown collection, 409 schema conflict on upsert, 416 unsatisfiable range, 422 invalid name or upload; writes on a readonly worker return 405.

There is no CQL, JSON feature response, overview level, id lookup, cursor paging or manifest. Filters and bboxes are client-side.

Collection metadata

GET /v2/collections/{id} returns name, version, idColumn, geometry, columns, rows, bytes, etag and url. GET /v2/collections returns name, version, idColumn, geometry, rows, bytes and url for each collection under collections.

PostgreSQL schema

pgpq.collections        name, version, id_column,
                        geometry, columns_json, rows,
                        bytes, updated
pgpq.shards             shard_id, bytes, data_start,
                        data_end, rows, first_key,
                        last_key, created
pgpq.collection_shards  collection, version, seq,
                        shard_id, virtual_base
pgpq.shard_chunks       shard_id, no, data bytea
pgpq.virtual_files      collection, version, footer,
                        footer_start, total_length, etag
pgpq.ids                collection, hash, id, shard_id

Shard payloads are 8,120-byte bytea chunks read by primary key; shard bytes are not compressed again. virtual_files caches the footer per version. The small ids index exists only to find upsert candidates.

Explanation

Diátaxis explanation

Why the server stops at bytes, and what that costs.

Synthesized footer

Concatenating complete files would leave several footers and wrong offsets. pgpq serves shard payloads unchanged and writes one footer with row groups rebased to virtual positions; the byte map translates ranges back. There is no second copy and no mutation, so standard readers see one file.

Immutable versions

A version lists shard references. Merges write new shards and commit a new version; published shards never mutate. Readers pin one ETag or version, so merges need no locks and cannot tear reads. The pointer advance is one transaction; old shards stay readable while referenced, so rollback is a pointer change.

No query catalog

There is no cells table, overview samples, CQL evaluator or cursor state. Parquet row-group statistics plus client bbox and filter logic replace the server query layer. The only server lookup is the small id → shard index for upsert. That removes many invariants, but the server cannot answer bbox or attribute queries, counts, or GeoJSON.

Footer-size risk

The footer is fetched first on almost every cold read, so its size is on the critical path. It grows with shard count and with row groups and column chunks per shard; many small shards can make metadata dominate a small range. Mitigations are larger row groups, bounded shards, cached footers and a footer-bytes term in the size contract. Rebasing column-chunk and page-index offsets is the delicate part.

Limits

  • Clients do all filtering, bbox work and counts. There is no server query language, CQL, feature JSON or GeoJSON response.
  • No overviews, id lookup endpoint, cursor paging or manifest. Collection metadata and listing exist; the virtual file is the only feature response.
  • One geometry column and one CRS per collection; no reprojection.
  • Native GeoParquet 2.0 only; no runtime converter, DuckDB, GDAL or cgo.
  • 512 MiB is a target ceiling; an unsplittable row group may exceed it, and a single oversized feature is rejected.
  • Upserts depend on the id index; non-id attributes are not indexed.
  • Footer size and cold-read cost are unmeasured; many small shards may make the footer dominate.
  • Writes run only on writable workers; public traffic is readonly. Auth and TLS live in the adjacent proxy.
