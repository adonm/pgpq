postfgb v2 · design

Code budget · production Go for v2

Now: about 1,920 of 4,000 lines (48%).

With the id-run merge and reaping: about 2,000 lines (50%).

Outside the budget: about 1,070 lines of tests and 66 lines of SQL.

Decisions

  • builtPartition unit
    S2 level 8, a fixed grid with no per-collection setting.
  • builtChunk size
    2 MiB or 50,000 features. Kept; retune only after measuring.
  • builtSparse partitions
    No packing. Every populated cell keeps at least one chunk.
  • builtOverview levels
    8 and 10 per cell; 12 above 100,000 features; 6, 4 and 2 per cell, rebuilt in the commit. Cap 256.
  • builtSamples and zoom
    Full geometry, no simplification yet. No zoom mapping on the server: the client asks for overview=N.
  • builtConditional loads
    base=s answers 409 when a listed cell changed after s.
  • builtCaches
    Three LRUs per worker, 256 MiB each: file bytes, chunk lists, decoded id runs.
  • decidedUpload
    One .fgb.zst per L8 cell. No streaming, bucketing or spill. Not built: the /v2 load still takes multi-cell bodies.
  • decidedSnapshot per upload
    Each upload is one commit. A multi-cell reload is not atomic: readers can see old and new cells together until it ends.
  • nextId runs
    One run per upload. Lookups search every live run. Above 64 live runs, a background merge combines the smallest and drops stale entries.
  • nextReaping
    Keep 72 h retention. Delete rows and files that no retained snapshot can see.
  • cutPostings
    Zone maps and column files answer filters for now. Revisit if a dense-cell filter takes over 1 s cold.
  • cutId-run Bloom filters
    A binary search over at most 64 runs is cheap.

Risks

  • Loads are held in memory and nothing spills. The densest cell (about 1.2 GB of FGB at 1e9 features) sets the worker’s memory.
  • A reload of many cells is not one snapshot. Readers can see a mix of old and new cells until the last upload commits.
  • Id runs are delta-coded, so a lookup decodes each live run in full. At 1e9 features the runs total about 15 GB: a fence index per run is needed before lookups scale.
  • The coarse rebuild reads sibling samples on every upload. Measure at 10 million features.
  • Dense cities at zoom 13 hold about 240k features on screen. Use overviews until detail is small, around zoom 16 or 17.
  • Overview responses carry full geometry, so they can be large.
  • Filters on dense cells scan column files until postings exist.
  • Collections loaded before migrations 0032 to 0034 need a reload before lookups and filters work.

Terms

  • Key: the S2 level-30 cell of a feature’s bbox centre. Sets the storage order.
  • Partition: an S2 level-8 cell, the unit of upload, load and replacement.
  • Chunk: an immutable FlatGeobuf with a column file and a zone map, and one catalog row.
  • Sample: the 256 smallest-hash features of a cell, stored as chunks with level = N.
  • Id run: sorted (hash, key) pairs, one per upload.
  • Snapshot: one upload’s commit. A row is visible at s when begin ≤ s < end.
  • Virtual file: a file’s bytes stored as block rows, read back through the file-bytes overlay.
