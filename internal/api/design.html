Design contract · C4 + Diátaxis

GeoParquet 2.0 inside PostgreSQL.

One logical GeoParquet file per S2 L8 cell, stored as 8,120-byte inline bytea chunks. Native Parquet geometry and row-group statistics do spatial pruning; no tile pyramid and no sidecar index.

System context

C4 L1

Who uses pgpq and what sits outside it. No internal components or timing.

Assumptions

  • One PostgreSQL holds the catalog and cell payloads.
  • DuckDB is the loader format; the server shells out to the CLI.
  • Updates are batched, typically hourly.
  • No auth or TLS inside pgpq.

How to test a small OSM chunk

Diátaxis how-to

Use one small extract and one layer at a time. This is task guidance, not part of the topology.

  1. Use a city-sized PBF, not a country extract. Monaco (~1 MB) or Andorra (~4 MB) is enough; avoid Île-de-France and Luxembourg for routine tests.
  2. Prepare a DuckDB file with one view per layer and a layer_catalog row for each: view, id, geometry. Keep buildings, places and roads in separate views.
  3. Run one test worker on :8094 with GOMEMLIMIT=1GiB and the DuckDB CLI path. Do not point tests at public :8080/:8081.
  4. Load one view, run bbox/filter/id/GeoParquet checks, delete the test collection, then move to the next layer. Never run all layers concurrently.
PGPQ_DUCKDB=/path/to/duckdb \
GOMEMLIMIT=1GiB bin/pgpq serve \
  --addr 127.0.0.1:8094

curl -X POST -T layers.duckdb \
  -H 'Content-Type: application/vnd.duckdb' \
  'http://127.0.0.1:8094/v2/collections/buildings?view=layer_buildings'

curl 'http://127.0.0.1:8094/v2/collections/buildings/items?bbox=7.41,43.73,7.43,43.75&limit=100'

curl 'http://127.0.0.1:8094/v2/collections/buildings/items?bbox=7.41,43.73,7.43,43.75&limit=1000&f=geoparquet' \
  -o page.parquet

For a raw PBF, use osmium extract and osmium tags-filter before converting; retain the filtered extract only. The repository harness is the repeatable path once the background OSM iteration lands.

Explanation

Diátaxis explanation

L8 partition

A cell is small enough for bbox pruning and large enough to avoid catalog noise. L6/L4/L2 are sampled projections of the same data.

2,048 rows

Row-group statistics balance point lookups against wide scans. More groups lower scan cost but add footer/index overhead.

Hourly batches

One POST per batch rewrites each touched cell once. A 1M-row cell costs about 21 s and 10 MB of movement; per-row updates are intentionally not supported.

No tile pyramid

The filtered GeoParquet response is the portability boundary. No FGB index, no vector-tile service, no sidecar partition files.

Limits

  • DuckDB ingest requires the external duckdb binary and spatial extension; the server never links DuckDB.
  • One root geometry column, OGC:CRS84/EPSG:4326 only. Nested schema and multiple geometry columns are deferred.
  • One-file-per-cell append is for hourly batches. Use PUT for a full snapshot; avoid per-row appends.
  • Filtered numberMatched scans surviving row groups; it is not a posting-list count.
  • About 4,145 production Go lines, one migration baseline, no FGB/v1 code.
