The choices behind the numbers, and what they cost.

Tradeoffs

Whole-cell replace, no snapshots. A commit deletes the cell’s old rows and files and writes the new ones in one transaction. That keeps reads on current data and removes reaping, but the commit costs the cell’s size and a racing read retries once. L6 is rebuilt in the commit; L2 is queued for the background worker.

Three levels, more scanning. Levels 8, 6 and 2 are stored, with 512, 2,048 and 2,048 samples per cell. L8 is built at load, L6 in the commit and L2 by a background worker. At high zoom a dense view holds hundreds of thousands of features; a page reads only the ranges its R-tree names. Coarse views use the samples instead.

Parquet, not a hand-rolled sidecar. A Parquet column file with 2,048-row groups writes min/max into its footer, so a filter reads stats and only the predicate columns. That adds a dependency, but it removes the whole-sidecar scan.

Id rows, not runs. One index row per feature: a lookup is a few B-tree pages plus one file’s blocks, well under 1 MB. Count the row and its primary-key entry and it costs about 80 B per feature, or about 75 GB at 1e9. Every table keys on a 2-byte collection id, and the name lives once in collections. A compact chunked index would need background merges to keep hash-to-cell routing.

Sort and encode run in the loader. The upload must be a canonical FlatGeobuf in (key, id) order with its R-tree. The server checks it and only derives the fence, Parquet columns and id rows. That takes about 70% of the ingest CPU off the server, at the cost of a stricter upload contract and trusting the loader’s index after checking its root.

One file per partition. One virtual FlatGeobuf per L8 cell: about 100k files instead of 450k chunks, one header each, and the FGB R-tree does the spatial pruning. Its Parquet sidecar groups columns into 2,048-row groups.

Two indexes, two questions. The R-tree finds a bbox; a key fence every 256 features resumes a cursor, reaches a filtered row and turns an id into a byte range. A dense partition’s R-tree is about 7 MB to read once and cache.

Decisions

  • builtPartition unit
    S2 level 8, a fixed grid with no per-collection setting.
  • decidedUpload contract
    A canonical FlatGeobuf in (key, id) order with its R-tree, written by the loader. The server validates it and derives the fence, columns and id rows. Sort and encode do not run on the server. Not built.
  • decidedPartition file
    One FlatGeobuf per L8 cell, sliced into 8 KB uncompressed pieces and block-compressed, with a key fence every 256 features. The code still chunks.
  • decidedColumns
    One Parquet column file per partition, rows in the same (key, id) order, 2,048-row groups. Row-group min/max is the zone map; a filter reads stats, skips groups and projects only the predicate columns. The code still uses the PFA1 sidecar.
  • decidedOverview levels
    8 for every partition, 6 and 2 per cell. Caps: 512 features per L8 sample, 2,048 for L6 and L2. L8 is built at load, L6 in the commit, L2 by a background worker after 5 s quiet or 60 s at most. Detail reads the L8 file through its R-tree.
  • decidedIngest
    Each upload is one level-8 cell; the server reads only that body and writes only that cell’s rows. Not built: the /v2 load still takes multi-cell bodies.
  • decidedSamples and zoom
    Full geometry, no simplification. L8 keeps 512 per cell; at z12 the viewport is one to a few L8 cells, so 512 fills a 1k page, while 2,048 would add about 120 GB for no extra page. L6 and L2 keep 2,048. The cap is per cell, so a transition zoom that covers part of a cell can still under-fill; the figure’s 4×3 view shows that. No zoom mapping on the server: the client asks for overview=N. L2 is eventually consistent.
  • builtCaches
    Two LRUs per worker, 256 MiB each: block bytes and the collection catalog. Target: per-cell file rows, keyed by cell and version.
  • builtPaging
    A cursor is the (key, id) of the last feature returned. Each page reads the current rows, so a walk follows uploads that land between pages. Cursors never expire.
  • builtId index
    One row per feature: its id hash and key. Replaced with the cell on every upload. No runs, merges or Bloom filters.
  • decidedCollection id
    A smallint id in every table; the name lives only in collections. That caps collections at 32,767, and int is the fallback beyond it. Not built: the code still uses the bigint uid.
  • builtCleanup
    Replaced rows and files are deleted in the same commit as the new ones. A read that raced a commit retries once.

Risks

  • Loads are held in memory and nothing spills. The densest cell (about 2.5 million features) decodes to about 2.2 GB and sets the worker’s memory.
  • A filter on a dense cell reads one predicate column from the Parquet file plus matched FGB blocks. Row-group stats skip groups, but a broad filter can still approach the column bytes, and equality on high-cardinality fields prunes poorly.
  • numberMatched has Parquet row-group stats but no postings: it reads one predicate column across surviving groups and cannot stop early.
  • L2 samples are deferred: a commit queues the L2 parent and a background worker rebuilds it after up to 60 s, so coarse views can lag detail and L6.
  • A commit deletes and rewrites the cell under the collection lock: a dense cell serializes uploads for seconds, and every upload pays one commit.
  • The id index holds one row per feature. At 1 billion features that is about 74.5 GB in Postgres, and every upload inserts or deletes the cell’s rows.
  • A walk that spans an upload can skip features added behind its cursor, and repeat one moved ahead of it. Each page is still one read.
  • The server trusts the loader’s R-tree after checking the index root, order, cell and ids. A wrong index can hide rows without corrupting them.
  • A read can list a file just before a commit deletes it. It retries once against the new list, so under a heavy write rate some requests are slower.
  • Only levels 8, 6 and 2 are stored. At z7 one L2 cell has 2,048 samples, but the figure’s 4×3 view covers about 10% of the cell and shows only ~203; a 1,920×1,080 view covers ~58% and shows ~1,200. L2 is still coarse at z8–10, and the transition zooms can under-fill. Adding L4 is the clean fix if that matters.
  • Dense cities at zoom 13 hold about 247,800 features on screen, about 52 MB over the link. Use overviews until detail is small, around zoom 17.
  • An L8 sample of 2,048 would cost about 161 GB across 393k partitions, eight times the 512 cap, for a zoom where one to a few cells already fill the page. That is why L8 stays at 512.
