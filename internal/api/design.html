Now: about 1,920 of 4,000 lines (48%).

Outside the budget: about 1,070 lines of tests and 66 lines of SQL.

Decisions

  • builtPartition unit
    S2 level 8, a fixed grid with no per-collection setting.
  • builtChunk size
    2 MiB of uncompressed FGB or 50,000 features. Kept; retune only after measuring.
  • builtSparse partitions
    No packing. Every populated cell keeps at least one chunk.
  • decidedOverview levels
    8 for every partition, 6 and 2 per cell, each built per upload from the cell below. Detail is not stored: it reads the L8 chunks whose envelope meets the bbox. Level 4 and 12 are cut. Cap 256 per cell.
  • decidedIngest
    Each upload is one level-8 cell. The server reads only that body and writes only that cell’s rows.
  • builtSamples and zoom
    Full geometry, no simplification yet. No zoom mapping on the server: the client asks for overview=N.
  • builtConditional loads
    base=s answers 409 when a listed cell changed after s.
  • builtCaches
    Three LRUs per worker, 256 MiB each: file bytes, chunk lists, decoded id runs.
  • decidedUpload
    One .fgb.zst per L8 cell. No streaming, bucketing or spill. Not built: the /v2 load still takes multi-cell bodies.
  • decidedSnapshot per upload
    Each upload is one commit. A multi-cell reload is not atomic: readers can see old and new cells together until it ends.
  • builtPaging
    A cursor is the (key, id) of the last feature returned. Each page reads the latest snapshot, so a walk follows uploads that land between pages. Cursors never expire.
  • nextId runs
    One run per upload. Lookups search every live run. Above 64 live runs, a background merge combines the 16 smallest and drops stale entries.
  • nextReaping
    Replaced rows and files stay 15 minutes, then are deleted. Nothing pins a snapshot, so there is no 72 h retention.
  • cutPostings
    Zone maps and column files answer filters for now. Revisit if a dense-cell filter takes over 1 s cold.
  • cutId-run Bloom filters
    A binary search over at most 64 runs is cheap.

Risks

  • Loads are held in memory and nothing spills. The densest cell (about 2.5M features) decodes to about 1.2 GB and sets the worker’s memory.
  • A filter on a dense cell reads every chunk until postings exist: about 300 MB per request in the worst case (see Costs).
  • A reload of many cells is not one snapshot. Readers can see a mix of old and new cells until the last upload commits.
  • A walk that spans an upload can skip features added behind its cursor, and repeat one moved ahead of it. Each page is still one snapshot.
  • Id runs are delta-coded, so a lookup decodes each live run in full. At 1e9 features the runs total about 15 GB: a fence index per run is needed before lookups scale.
  • Coarse zoom, dense data: below about zoom 10 a dense view is served by levels 6 and 2. A page that lags the zoom overscans: at zoom 7 a 1,000-feature page falls through to level 2 while the view holds about 1.9M features.
  • Dense cities at zoom 13 hold about 240k features on screen, about 24 MB over the link. Use overviews until detail is small, around zoom 16 or 17.
  • Overview responses carry full geometry, so they can be large.
  • Collections loaded before migrations 0032 to 0034 need a reload before lookups and filters work.

Terms

  • Key: the S2 level-30 cell of a feature’s bbox centre. Sets the storage order.
  • Partition: an S2 level-8 cell, the unit of upload, load and replacement.
  • Chunk: an immutable FlatGeobuf with a column file and a zone map, and one catalog row.
  • Sample: the 256 smallest-hash features of a cell, stored as chunks with level = N.
  • Id run: sorted (hash, key) pairs, one per upload.
  • Snapshot: one upload’s commit. A row is visible at s when begin ≤ s and s < end.
  • Cursor: the (key, id) of the last feature a page returned. It carries no snapshot; each page reads the latest one.
  • Virtual file: a file’s bytes stored as block rows, read back through the file-bytes overlay.
