Design contract · Oct 2026

GeoParquet 2.0 inside PostgreSQL.

One logical GeoParquet file per S2 cell, stored as 8,120-byte inline bytea chunks. Native Parquet geometry and statistics do the spatial work; no sidecar index and no tile pyramid.

DuckDB upload GeoParquet 2.0 inline 8,120 B chunks append-compacted L8 cells no build step cgo-free core

Data flow

One view = one collection

An optional layer_catalog supplies the view, id column and geometry column. Otherwise the collection name is the view and id_column is required.

Pure PostgreSQL

No extensions, no object store, no sidecar files. Readers need only SELECT; writes are ordinary transactions.

Writes and compaction

MethodSemantics
PUTreplace the collection or the listed cells; full compaction
POSTmerge into affected L8 cells; rewrite only those cells and parent samples

A cell is always one GeoParquet file with 2,048-row groups, sorted by (Hilbert key, id). An append is a synchronous compaction: read the old cell, merge by id, sort, write a new cell file and new chunk rows, replace the catalog pointer, and delete the old chunks in the same transaction. There is no small-file backlog.

Heavy cell result

Hourly batch model. A one-row append to a 1M-row cell rewrites the whole 10 MB cell in 20.9 s and uses 1.39 GB RSS. That is acceptable for one batch per cell per hour, not for per-row updates.

Batch writes

Send one POST per hourly batch. Each touched cell is read, merged, sorted and rewritten once; untouched cells are not rewritten. The catalog stays one row per cell and there are no small-file fragments to compact.

Size the writable worker for the largest cell in the batch: a 1M-row cell needs about 1.4 GB peak. Fragment compaction is deferred until the update cadence or cell size makes a 21 s rewrite too expensive.

Read path

Vector-tile replacement: items?bbox=…&overview=6&f=geoparquet

Returns one filtered GeoParquet 2.0 file for the view. Clients can stream or map it; no tile pyramid and no per-tile endpoint.

IDs use a hash → (cell,row) pointer and Parquet SeekToRow. Cursors resume by (key,id).

Rules

Native geometry

Parquet GEOMETRY/WKB, OGC:CRS84. One root geometry column.

One zstd layer

Parquet pages compress internally. Chunks are raw bytes, never compressed again.

Chunked cell

8,120 bytes per chunk, one 8 KB page inline, primary-key range reads.

S2 L8 compaction

L8 is the partition; 2,048-row groups sorted by spatial key. Appends rewrite only touched cells.

No build HTML

This page is one static file served directly. Bootstrap is a CDN stylesheet; diagrams are inline SVG/CSS.

Limits and open work

DuckDB ingest requires the external duckdb binary and spatial extension; the server never links DuckDB. A cell is decompressed logically through Parquet ranges, and dense cells should be sized for the worker memory budget.
  • One geometry column, root-level attributes, OGC:CRS84/EPSG:4326 only.
  • One-file-per-cell append is intended for hourly batches; use PUT for a full snapshot and avoid per-row appends.
  • Filtered numberMatched scans surviving row groups; it is not a posting-list count.
  • About 4,145 production Go lines. The remaining bulk is CQL and the GeoParquet reader/writer.
