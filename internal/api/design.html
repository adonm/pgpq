pgpq v2 contract

PostgreSQL-backed GeoParquet 2.0. One native Parquet geometry column, one GeoParquet bytea per spatial cell, and one virtual GeoParquet response per collection or overview. Parquet pages use zstd internally; the server does not add a second compression layer. Large cells are read as external-TOAST ranges, not whole values.

Shape

Upload
DuckDB file. A view becomes a collection; layer_catalog supplies view, id and geometry columns. The writable worker invokes the DuckDB CLI and exports the view.
Storage
A GeoParquet 2.0 cell file with native GEOMETRY/WKB, row groups of 2,048 and zstd-compressed Parquet pages, stored as one bytea in pgpq.cells.
Read
Catalog bbox/zone pruning, then Parquet row-group geospatial statistics, then exact bbox/filter evaluation. JSON or filtered GeoParquet.
Tile replacement
items?bbox=…&overview=6&f=geoparquet is a virtual GeoParquet file for that view, filtered at the requested bbox and zoom level.

Ingest

  1. Receive a DuckDB file at PUT /v2/collections/{id}. The path name selects the collection; view= selects a view when the catalog has a different layer name.
  2. If layer_catalog exists, read view_name, id_column and geom_column. Otherwise use id_column= and a geometry column.
  3. Export the view to a Parquet staging file with DuckDB; read it with the same native GeoParquet reader used by the direct GeoParquet compatibility path.
  4. Assign every feature to a level-8 S2 cell by geometry bounds, sort by Hilbert key and id, and write one GeoParquet file per cell.
  5. Insert the GeoParquet file as one bytea cell row; Parquet already compressed its pages with zstd. Build L6/L4/L2 samples from the same in-memory feature set and commit them in the same transaction.

The core is cgo-free. DuckDB is an external command, configured by PGPQ_DUCKDB. Direct GeoParquet 2.0 upload is kept as a compatibility path for migrations.

Cell format

ItemValue
Geometrynative Parquet GEOMETRY, WKB, OGC:CRS84
Attributesroot primitive columns; bool, int64, double, string, JSON
Row order(__pgpq_key, id); key is the ordered S2 Hilbert key
Row groups2,048 rows; native geospatial bbox statistics per group
CompressionParquet pages zstd-compressed internally; the bytea is not compressed again
MetadataGeoParquet geo key with version 2.0.0, primary column, WKB and bbox

The hidden __pgpq_key column is not returned in GeoJSON. It lets the reader skip row groups before a cursor and keeps each cell deterministic.

Catalog

pgpq.collections  uid, name, version, id_column, geometry, columns_json
pgpq.cells        collection_uid, level, cell, features, bounds, key range, zone, data bytea
pgpq.ids          collection_uid, hash, cell, row

The catalog carries only scalar pruning data. Reading a cell fetches and decompresses exactly one bytea; no block table and no sidecar file lookup.

Read path

  1. Prune cells with collection bounds and the per-cell numeric zone.
  2. Parse the footer from a TOAST slice. Small cells are fetched whole; large cells read 64 KiB ranges through substring, so Parquet page/footer ranges stay lazy.
  3. Skip row groups whose native geospatial bbox or attribute statistics cannot match.
  4. Read surviving rows, apply exact bbox/filter checks, and stop at the page limit.
  5. Serialize the page as JSON (default) or GeoParquet 2.0 (f=geoparquet).

IDs use the pgpq.ids hash-to-(cell,row) pointer and Parquet SeekToRow; no whole-cell scan. Cursors resume by (key,id) and use the hidden key column to skip row groups.

Overview levels

L8 is detail. L6, L4 and L2 keep up to 2,048 sampled features per cell. Sampling drops subpixel areas and lines (about 100 m at L6, 400 m at L4 and 1.6 km at L2 at 48°N) while keeping points. All levels are built in the write commit; there is no deferred worker.

Why this replaces vector tiles

A client asks for a bbox and an overview level. The response is a valid GeoParquet 2.0 file containing only the rows the server kept, with geometry and attributes. Clients that understand GeoParquet can map or stream it directly; clients that do not can use the JSON endpoint. There is no tile pyramid, no FGB R-tree and no per-tile endpoint.

Limits

  • Small cells are fetched whole; large cells use external-TOAST slices. Dense cells should still be sized for the worker memory budget; the writer caps concurrent cells at two.
  • DuckDB ingest requires the external duckdb binary and the spatial extension. Reading/querying a loaded collection does not.
  • Geometry columns must be root columns and use OGC:CRS84/EPSG:4326. Nested schema and multiple geometry columns are not supported yet.
  • numberMatched with a filter scans surviving row groups; it is not a posting-list count.
  • The server is cgo-free by design; DuckDB is never linked into the process.

Detail data is 41 MB for 100k warm features, 21 MB for 228k Luxembourg buildings, and 4.8 MB for 4,628 enriched Monaco features. The current PostgreSQL database is about 300 MB.

Range proof: a 64-byte slice of a 9 MB external cell touched 8 shared buffers; reading the whole value touched 142. The cell reader uses 64 KiB aligned slices and a small per-file cache.

Code size

About 3,978 production Go lines. The FGB format, block store, fence, prepared bundle, sidecar Parquet and pid index are gone. Remaining bulk is the CQL parser/evaluator and the GeoParquet writer/reader.

Decisions

  • built GeoParquet 2.0 native GEOMETRY/WKB cells.
  • built One GeoParquet bytea per cell with internal zstd pages; no separate block/file table.
  • built DuckDB upload with external CLI export; direct GeoParquet compatibility.
  • built Parquet native bbox/attribute statistics for pruning.
  • built JSON and filtered GeoParquet output.
  • built L2/L4/L6 samples in the write commit.
  • decided Vector tiles are replaced by bbox/overview-filtered GeoParquet.
