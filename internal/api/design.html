Upload and the id index scale with features, so both classes pay the same 186 GB up and 74.5 GB of id rows. Detail storage and ingest time grow with the cell count: 83k mean cells pay 83k commits and three sample files each, while 400 dense cells pay 400 large commits.

Tradeoffs

Whole-cell replace, no snapshots. A commit deletes the cell’s old rows and files and writes the new ones in one transaction. That keeps reads on current data and removes reaping, but the commit costs the cell’s size and a racing read retries once.

Three levels, more scanning. Levels 8, 6 and 2 are stored. At high zoom a read scans the level-8 files in view: in a dense cell a page can scan a few hundred thousand features. Coarse views use the samples instead.

Id rows, not runs. One index row per feature: a lookup is a few B-tree pages plus one file’s blocks, well under 1 MB. Count the row and its primary-key entry and it costs about 80 B per feature, or about 75 GB at 1e9. Every table keys on a 2-byte collection id, and the name lives once in collections. A compact chunked index would need background merges to keep hash-to-cell routing.

Sort and encode run in the loader. The upload must be a canonical FlatGeobuf in (key, id) order with its R-tree. The server checks it and only derives the fence, columns and id rows. That takes about 70% of the ingest CPU off the server, at the cost of a stricter upload contract and trusting the loader’s index after checking its root.

One file per partition. One virtual FlatGeobuf per L8 cell: about 100k files instead of 450k chunks, one header each, and the FGB R-tree does the spatial pruning.

Two indexes, two questions. The R-tree finds a bbox; a key fence every 256 features resumes a cursor, reaches a filtered row and turns an id into a byte range. A dense partition’s R-tree is about 7 MB to read once and cache.

Decisions

  • builtPartition unit
    S2 level 8, a fixed grid with no per-collection setting.
  • decidedUpload contract
    A canonical FlatGeobuf in (key, id) order with its R-tree, written by the loader. The server validates it and derives the fence, columns and id rows. Sort and encode do not run on the server. Not built.
  • builtPartition file
    One FlatGeobuf per L8 cell, sliced into 8 KB uncompressed pieces and block-compressed, with a key fence every 256 features.
  • decidedOverview levels
    8 for every partition, 6 and 2 per cell, each built per upload from the cell below. Detail is not stored: it reads the L8 file, using its R-tree to find the blocks a bbox needs. Level 4 and 12 are cut. Cap per cell.
  • decidedIngest
    Each upload is one level-8 cell. The server reads only that body and writes only that cell’s rows.
  • builtSamples and zoom
    Full geometry, no simplification yet. No zoom mapping on the server: the client asks for overview=N.
  • builtCaches
    Two LRUs per worker, each: file bytes and the file list.
  • decidedUpload
    One .fgb.zst per L8 cell. No streaming, bucketing or spill. Not built: the /v2 load still takes multi-cell bodies.
  • builtPaging
    A cursor is the (key, id) of the last feature returned. Each page reads the current rows, so a walk follows uploads that land between pages. Cursors never expire.
  • builtId index
    One row per feature: its id hash and key. Replaced with the cell on every upload. No runs, merges or Bloom filters.
  • decidedCollection id
    A smallint id in every table; the name lives only in collections. That caps collections at 32,767, and int is the fallback beyond it. Not built: the code still uses the bigint uid.
  • builtCleanup
    Replaced rows and files are deleted in the same commit as the new ones. A read that raced a commit retries once.

Risks

  • Loads are held in memory and nothing spills. The densest cell (about features) decodes to about and sets the worker’s memory.
  • A filter on a dense cell reads the whole partition file: about per request in the worst case (see Risks).
  • A walk that spans an upload can skip features added behind its cursor, and repeat one moved ahead of it. Each page is still one read.
  • The id index holds one row per feature. At features that is about in Postgres, and a lookup reads one hash’s rows plus one file’s blocks.
  • The server trusts the loader’s R-tree after checking the index root, order, cell and ids. A wrong index can hide rows without corrupting them.
  • A read can list a file just before a commit deletes it. It retries once against the new list, so under a heavy write rate some requests are slower.
  • Coarse zoom, dense data: below about zoom a dense view is served by levels 6 and 2. A page that lags the zoom overscans: at zoom 7 a -feature page falls through to level 2 while the view holds about features.
  • Dense cities at zoom 13 hold about features on screen, about over the link. Use overviews until detail is small, around zoom .
  • Overview responses carry full geometry, so they can be large.
  • Collections loaded before migration 0035 need a reload: the row layout changed and snapshots are gone.
